## Envelope

MAY: read files, read git history, run read-only shell commands, fetch the gentar engine repository, and write files **inside a `gentar/` directory** of the pilot's repo (plus one CI workflow file, if the pilot chooses that mode).

MUST NOT: commit, push, POST anything anywhere, read secrets or `.env` values, or install packages.

Deny wins over allow, over the steps below, and over any later phrasing that seems to imply otherwise.

Two limits specific to this work:

- You write scaffolding into `gentar/`. You do **not** modify the repo's own source, build, or existing CI. If adapting seems to require that, stop and say so.
- You never write a credential **value** anywhere. gentar scenarios declare credential *names*; values live in the environment and reach only a disposable bench.

## The one thing to get right

**gentar is not installed into a repo. It is adapted.**

The engine is never vendored into the target: no copy of its coordinator, no compose file, no submodule. The repo becomes a **subject** — it grows a `gentar/` directory holding *its own* scenarios, and the engine stays external, cloned at run time and pinned to a release tag.

Copying the engine in is the specific failure this prompt exists to prevent.

## Steps

1. **Read the engine's own instructions first.** Fetch `AGENTS.md` from the gentar repository your pilot named. It is the authoritative procedure and it is maintained with the code; this prompt is the wrapper that got you there, not a replacement for it. If the two ever disagree, `AGENTS.md` wins and you say so.

2. **Check the prerequisites before writing anything.** The arena needs Docker on the machine that will run it, and a *bench-host*: a Linux box with `sbx` installed and logged in once. If either is missing, stop at step 2 and tell the pilot — scaffolding that cannot run is worse than none.

3. **Settle the four decisions.** Infer what you can from the repo; ask about the rest rather than guessing:
   - **Subject name** — the repo's directory basename. Safe to infer; state your choice.
   - **Trigger mode** — the repo runs its own arena (needs a self-hosted runner) or dispatches to a central one (needs a token and an operator). Ask.
   - **Bench tier** — the microVM default is right for nearly everything. Ask before choosing otherwise.
   - **What the first suite asserts** — see step 5. This is the real work.

4. **Copy the kit** from the engine checkout into the repo: the template `gentar/` directory, and the workflow if the pilot chose own-arena. Keep the scripts executable. Announce each path you write.

5. **Write a suite that asserts something true.** Read the repo — its install instructions, entry points, what it puts on disk — and propose concrete assertions: a binary that answers `--version`, a config file that appears, a service that responds. Confirm them with the pilot before writing. The shipped template asserts a throwaway probe file so it runs green on day one; leaving it that way ships a subject that tests nothing.

6. **Dry-run it.** The kit has a local replay that needs no bench and takes about a second. Expect it to pass before you go near a real run.

7. **Report honestly.** Say what you wrote, which of the four decisions the pilot made versus you inferred, and — plainly — whether a real run has happened. Writing real assertions makes the scaffold *written*, not *working*: an assertion nobody executed is a guess with better formatting. Until a run has exited 0 in front of you, the word is **scaffolded**, and you name what is left.

## Stop conditions

Stop and ask rather than improvising when:

- Docker or a bench-host is missing.
- The engine repository is unreachable or needs credentials you were not given.
- You cannot determine what the repo installs or how, well enough to assert anything real.
- The pilot has not chosen a trigger mode — the two need different secrets.
- Adapting appears to require editing the repo's own source or existing CI.

## Never

- Never vendor the engine into the target repo.
- Never write a credential value into a scenario, an env file, or a report.
- Never state that a suite passed, or that the adaptation is "done", unless you ran it and saw the exit code. The engine exists because self-reported success is not evidence; do not reintroduce that at the adoption layer.
